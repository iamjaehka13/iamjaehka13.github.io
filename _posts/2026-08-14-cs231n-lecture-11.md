## **0. 이 글의 목표**

[Lecture 10의 video understanding](/posts/cs231n-lecture-10/)까지는 model이 입력을 어떻게 표현하고 처리하는지에 집중했다. 그러나 parameter가 수백억 개를 넘고 sequence가 길어지면 좋은 architecture만으로는 학습을 시작할 수 없다. Model state와 activation이 한 GPU memory를 넘고, 여러 GPU를 붙인 뒤에는 계산보다 통신과 대기 시간이 더 큰 병목이 될 수 있다.

이번 글의 핵심 질문은 다음과 같다.

- GPU의 Tensor Core가 높은 peak FLOPs를 내는 조건
- GPU·server·rack·pod로 멀어질수록 달라지는 통신 비용
- Data Parallelism이 큰 batch의 gradient와 같은 값을 만드는 이유
- FSDP가 parameter·gradient·optimizer state의 복제를 없애는 방법
- Activation checkpointing이 memory를 줄이는 대신 추가하는 계산
- HFU와 MFU가 서로 다른 utilization을 측정하는 이유
- 긴 sequence, 깊은 layer, 넓은 hidden dimension을 각각 나누는 CP·PP·TP
- 여러 병렬화 축을 물리적 cluster topology에 맞추는 4D parallelism

핵심은 **GPU 수를 늘리는 것 자체가 아니라, model의 각 tensor 축을 나누고 통신을 계산 뒤에 숨겨 모든 device에 지속적으로 유효한 일을 공급하는 것**이다.

## **1. 단일 GPU에서 GPU cluster로의 확장**

### **1.1 H100의 memory hierarchy와 Tensor Core**

GPU는 많은 연산 장치를 병렬로 움직이는 throughput processor다. NVIDIA H100 SXM을 예로 들면 80 GB HBM과 약 3.35 TB/s의 memory bandwidth, 50 MB L2 cache, 132개의 활성화된 Streaming Multiprocessor(SM)를 갖는다.

![H100 전체에서 HBM·L2 cache·SM·FP32 core·Tensor Core로 확대되는 GPU 구조]({{ '/assets/img/posts/cs231n-lecture-11/animations/gpu-architecture.gif' | relative_url }})

Memory는 연산 장치에 가까울수록 작고 빠르다.

1. HBM은 model state와 큰 activation을 보관한다.
2. L2 cache는 여러 SM이 재사용하는 data를 더 가까이 둔다.
3. SM 내부의 L1/shared memory와 register는 현재 tile의 operand를 공급한다.
4. FP32 core와 Tensor Core가 실제 arithmetic을 수행한다.

FP32 core의 fused multiply-add

$$
a x+b
$$

는 multiplication과 addition을 각각 세어 2 FLOPs다. Tensor Core는 같은 종류의 연산을 작은 matrix tile 단위로 처리한다. Matrix multiplication을 충분히 큰 tile로 묶고 input을 FP16·BF16처럼 낮은 precision으로 공급한 뒤 accumulation을 더 높은 precision으로 수행하면 훨씬 높은 throughput을 얻을 수 있다.

따라서 `float32` model을 GPU에 올렸다는 사실만으로 peak 성능이 나오지는 않는다. Tensor Core를 사용할 dtype, matrix shape, tile 크기와 data reuse가 함께 맞아야 한다. 작은 matrix나 memory에서 operand를 계속 다시 읽는 kernel은 peak FLOPs보다 bandwidth와 launch overhead에 먼저 막힌다.

### **1.2 Compute throughput의 세대별 증가**

![K40에서 B200까지 FP32 core와 Tensor Core의 peak throughput 증가]({{ '/assets/img/posts/cs231n-lecture-11/animations/gpu-throughput-growth.gif' | relative_url }})

최근 GPU의 큰 성능 증가는 범용 FP32 core의 증가만으로 나온 것이 아니다. Tensor Core의 도입, 낮은 precision, 더 큰 matrix engine과 memory system의 개선이 함께 작용했다.

그래프의 초기 FP32 수치와 최신 Tensor Core 수치는 precision과 연산 경로가 다르므로 동일한 workload의 순수한 speedup으로 읽을 수는 없다. 더 중요한 변화는 **deep learning이 활용할 수 있는 specialized matrix-compute envelope가 크게 넓어졌다는 사실**이다. 여기에 수천 개 GPU의 병렬화가 곱해지면서 단일 device 성능과 cluster scale이 동시에 증가했다.

### **1.3 GPU 간 연결의 계층적 bandwidth**

한 GPU 안의 HBM bandwidth가 매우 높아도 GPU 사이의 통신은 더 느리다. 연결 범위가 넓어질수록 이 격차는 커진다.

![H100 한 장에서 8-GPU server·rack·3072-GPU pod·24576-GPU cluster로 확장되는 계층]({{ '/assets/img/posts/cs231n-lecture-11/animations/cluster-bandwidth-hierarchy.gif' | relative_url }})

Llama 3 training cluster의 대략적인 계층은 다음과 같다.

| 범위 | 구성 | GPU 관점의 대략적 bandwidth |
|---|---:|---:|
| Device 내부 | HBM ↔ compute core | 3352 GB/s |
| Server 내부 | 8 GPUs | 900 GB/s |
| Pod 내부 | 3072 GPUs | 약 50 GB/s |
| Pod 사이 | 24576-GPU cluster | 50 GB/s 미만 |

이 구조를 이해할 때는 data center 전체를 **계층적인 memory와 interconnect를 가진 하나의 큰 컴퓨터**로 보는 편이 좋다. 가까운 GPU끼리는 빠르고, 멀리 떨어진 GPU끼리는 같은 tensor를 옮기는 비용이 훨씬 크다.

이 차이가 분산 알고리즘의 배치를 결정한다. Layer마다 activation collective를 수행하는 Tensor Parallelism과 parameter를 반복해서 all-gather하는 FSDP group은 빠른 NVLink domain 안에 두고, 통신 빈도가 상대적으로 낮은 축을 더 느린 inter-node link에 놓는 식이다. Peak FLOPs와 memory capacity만으로 실제 학습 성능이 정해지지 않는 이유다.

## **2. 분산 학습의 네 분할 축**

Transformer는 $L$개 layer가 다음 tensor를 반복해서 변환하는 구조로 볼 수 있다.

$$
X\in\mathbb{R}^{B\times S\times D}
$$

$B$는 batch size, $S$는 sequence length, $D$는 hidden dimension이다. 여기에 layer 축 $L$을 더하면 네 가지 기본 분할이 나온다.

![Batch·Sequence·Layer·Dim 축에 대응하는 Data·Context·Pipeline·Tensor Parallelism]({{ '/assets/img/posts/cs231n-lecture-11/slides/p30-four-parallelism-axes.png' | relative_url }})

| 방식 | 분할 축 | 각 GPU의 주된 작업 | 핵심 통신 |
|---|---|---|---|
| Data Parallelism(DP) | $B$ | 서로 다른 sample | gradient all-reduce |
| Context Parallelism(CP) | $S$ | 한 sequence의 서로 다른 token | KV block 교환 또는 all-to-all |
| Pipeline Parallelism(PP) | $L$ | 서로 다른 layer 구간 | boundary activation·gradient send/recv |
| Tensor Parallelism(TP) | $D$ | 한 layer의 matrix shard | all-gather·all-reduce |

네 parallel degree를 각각 $d_{DP},d_{CP},d_{PP},d_{TP}$라 하면 필요한 GPU 수는 다음과 같다.

$$
N_{GPU}
=
d_{DP}d_{CP}d_{PP}d_{TP}
$$

각 방식은 경쟁 관계가 아니다. Batch, sequence, layer, hidden dimension 중 어디에서 memory와 compute가 막히는지에 따라 서로 직교하는 축을 함께 사용한다.

## **3. Data Parallelism과 gradient 평균**

### **3.1 Global batch와 synchronous update**

$M$개 GPU가 각각 $N$개 sample을 처리한다고 하자. GPU $i$의 local loss를

$$
L_i(W)
=
\frac{1}{N}
\sum_{j=1}^{N}
\ell(x_{i,j},W)
$$

로 두면 global loss는 다음과 같다.

$$
L(W)
=
\frac{1}{M}
\sum_{i=1}^{M}L_i(W)
$$

Gradient의 linearity 때문에

$$
\nabla_W L
=
\frac{1}{M}
\sum_{i=1}^{M}
\nabla_W L_i
$$

가 성립한다.

![Global batch의 gradient를 GPU별 local gradient 평균으로 분해하는 과정]({{ '/assets/img/posts/cs231n-lecture-11/animations/data-parallel-gradient-equivalence.gif' | relative_url }})

즉 각 GPU가 local gradient를 계산하고 평균하면 $MN$개 sample을 한 device에서 처리한 gradient와 수학적으로 같다.

[Lecture 3의 minibatch SGD](/posts/cs231n-lecture-3/#32-전체-합-대신-minibatch)와 연결하면, DP는 작은 batch의 gradient를 여러 device에서 나눠 계산하는 방법이다. 다만 GPU 수를 늘리며 global batch 자체도 키우면 gradient noise와 optimization dynamics가 달라진다. 계산 분할의 등가성과 큰 batch의 학습 특성은 별개의 문제다.

### **3.2 Gradient all-reduce와 synchronous step**

각 GPU는 같은 parameter와 optimizer state를 복제하고 서로 다른 data shard를 읽는다.

![Model replica·서로 다른 local batch·gradient synchronization·model-state memory 한계로 이어지는 Data Parallelism]({{ '/assets/img/posts/cs231n-lecture-11/animations/data-parallel-synchronous-step.gif' | relative_url }})

한 iteration은 다음 순서다.

1. 각 rank의 서로 다른 minibatch loading
2. Local forward와 loss 계산
3. Local backward와 gradient 계산
4. Replica 사이의 gradient all-reduce
5. 모든 rank의 동일한 optimizer update

PyTorch `DistributedDataParallel`은 input을 자동으로 나누지 않는다. `DistributedSampler`나 동등한 data partition이 없으면 여러 GPU가 같은 minibatch를 중복 처리하는 버그가 생길 수 있다.

Synchronous update의 장점은 모든 replica가 같은 parameter state를 유지한다는 점이다. 각 worker가 독립적으로 여러 step을 진행하는 asynchronous SGD는 synchronization 대기를 줄일 수 있지만 stale parameter, 재현성과 debugging 문제가 커진다.

### **3.3 Backward-communication overlap**

Backward는 마지막 layer부터 gradient를 만든다. 마지막 쪽 parameter gradient가 준비되면 이를 bucket에 넣어 all-reduce하고, 동시에 GPU compute core는 앞쪽 layer의 backward를 계속할 수 있다.

$$
\underbrace{\text{backward of layer }\ell}_{\text{compute}}
\quad\parallel\quad
\underbrace{\text{all-reduce of layer }\ell+1}_{\text{communication}}
$$

이 overlap은 hardware가 training graph를 보고 자동으로 알아내는 일이 아니다. Runtime이 stream, dependency와 bucket schedule을 구성해야 하며 DDP가 일반적인 경로를 제공한다. 따라서 실제 step time은 compute time과 communication time의 단순 합보다 **얼마나 많이 겹칠 수 있는가**에 좌우된다.

## **4. Replicated model state의 memory 병목**

### **4.1 Parameter·gradient·optimizer state의 memory ledger**

DDP는 계산을 나누지만 model state는 GPU마다 복제한다. Parameter 수를 $P$라 하고 parameter, gradient, optimizer state가 차지하는 byte를 각각 $b_w,b_g,b_o$라 하면 GPU당 model-state memory는 대략 다음과 같다.

$$
M_{DDP}
\approx
P(b_w+b_g+b_o)
$$

[Lecture 3의 Adam](/posts/cs231n-lecture-3/#62-adam)은 parameter마다 1차·2차 moment를 유지한다. BF16 parameter와 gradient에 FP32 Adam moment 두 개를 쓰면 master weight를 제외해도 보통 다음과 같다.

$$
2+2+4+4=12\ \text{bytes/parameter}
$$

FP32 master weight까지 유지하면 16 bytes/parameter가 된다. 모든 항목을 2 bytes로 두는 단순한 lower-bound ledger에서는 8 bytes/parameter지만, 실제 값은 optimizer와 mixed-precision 구현에 따라 달라진다.

100B parameter는 8 bytes 가정에서도 800 GB다. 80 GB GPU 한 장에는 들어가지 않으며, DDP replica를 늘려도 각 GPU의 복제본 크기는 줄지 않는다.

### **4.2 FSDP의 parameter life cycle**

Fully Sharded Data Parallel(FSDP)은 parameter, gradient와 optimizer state를 data-parallel rank에 나눈다. World size가 $R$일 때 persistent model state는 이상적으로 약 $1/R$로 줄어든다.

$$
M_{FSDP,state}
\approx
\frac{P(b_w+b_g+b_o)}{R}
$$

대신 layer를 계산할 때는 해당 module의 full parameter가 필요하다.

![FSDP가 parameter shard를 모아 layer forward를 실행하고 임시 복제본을 해제하는 과정]({{ '/assets/img/posts/cs231n-lecture-11/animations/fsdp-forward-parameter-gather.gif' | relative_url }})

Forward에서의 life cycle은 다음과 같다.

1. 각 rank가 가진 parameter shard의 `all-gather`
2. Full parameter를 이용한 local-batch forward
3. 다음 layer parameter의 prefetch
4. 임시 full parameter 해제와 shard 형태 복귀

개념 그림에서는 한 GPU가 한 weight를 소유하고 broadcast하는 것처럼 볼 수 있다. 실제 FSDP는 보통 flat parameter를 모든 rank에 shard한 뒤 collective `all-gather`로 module parameter를 복원한다.

### **4.3 FSDP backward의 세 연산 중첩**

Backward에서도 parameter가 다시 필요하다.

![FSDP backward에서 parameter gather·local backward·gradient reduction이 겹치는 과정]({{ '/assets/img/posts/cs231n-lecture-11/animations/fsdp-backward-communication-overlap.gif' | relative_url }})

Steady state에서는 이웃한 layer에 대해 세 작업이 동시에 진행될 수 있다.

$$
\begin{aligned}
\ell-1 &: \text{parameter all-gather / prefetch} \\
\ell &: \text{local backward compute} \\
\ell+1 &: \text{gradient reduce-scatter}
\end{aligned}
$$

`reduce-scatter`는 replica의 gradient를 합치는 동시에 결과를 shard한다. Backward가 끝난 뒤 각 rank는 자신이 소유한 gradient shard와 optimizer state만 업데이트하고, 갱신된 parameter는 다음 forward의 all-gather에서 다시 모인다.

FSDP는 memory를 줄이는 대신 forward parameter all-gather, backward parameter all-gather, gradient reduce-scatter라는 통신을 추가한다. 성능은 다음 parameter prefetch, 현재 compute, 이전 gradient reduction을 얼마나 잘 overlap하는지에 달려 있다. CPU data loader도 다음 batch를 동시에 준비해야 Tensor Core가 input을 기다리지 않는다.

### **4.4 HSDP의 topology-aware group**

모든 GPU를 하나의 FSDP group으로 묶으면 느린 inter-node link까지 빈번한 parameter collective에 참여한다. Hybrid Sharded Data Parallel(HSDP)은 $K$개 GPU의 빠른 subgroup 안에서 FSDP를 수행하고, $M$개 subgroup 사이에는 replica 기반 DP를 수행한다.

![빠른 FSDP subgroup과 subgroup 사이 Data Parallelism을 결합한 HSDP]({{ '/assets/img/posts/cs231n-lecture-11/animations/hsdp-topology-aware-groups.gif' | relative_url }})

$$
N_{GPU}=M K
$$

- Intra-group: parameter all-gather와 gradient reduce-scatter
- Inter-group: 같은 shard에 대한 data-parallel gradient synchronization

통신량이 큰 FSDP 축을 server 내부 NVLink에 두고, 상대적으로 통신 빈도가 낮은 replica 축을 server 사이에 두면 physical network hierarchy와 algorithm hierarchy가 맞아진다.

## **5. Activation checkpointing의 memory-compute 교환**

FSDP가 model state를 나눠도 activation은 각 rank의 local input에 대해 남는다.

![Parameter state sharding 이후 Llama 3 규모에서 activation memory가 새 병목이 되는 과정]({{ '/assets/img/posts/cs231n-lecture-11/animations/activation-memory-bottleneck.gif' | relative_url }})

예를 들어 126-layer, hidden dimension 16384, sequence length 4096인 model에서 FFN expansion을 $4D$로 단순화하면, 각 layer의 FFN hidden activation 하나만 BF16으로 보관해도 batch dimension을 제외한 계산이 약 63 GiB다.

$$
126\times4096\times(4\times16384)\times2\ \text{bytes}
\approx63\ \text{GiB}
$$

Attention·normalization·residual computation에 필요한 다른 saved tensor까지 더하면 activation memory는 더 커진다.

### **5.1 Standard backpropagation의 activation 저장**

Layer $i$의 forward와 backward를 다음처럼 쓰자.

$$
A_{i+1}=F_i(A_i)
$$

$$
G_i=F_i^{\leftarrow}(A_i,G_{i+1})
$$

Backward가 $A_i$를 필요로 하므로 일반적인 autograd는 forward activation을 저장한다.

![Forward activation을 모두 저장한 뒤 역순으로 gradient를 계산하는 standard backpropagation]({{ '/assets/img/posts/cs231n-lecture-11/animations/standard-backprop-memory.gif' | relative_url }})

$N$개 layer가 모두 일정한 compute와 activation 크기를 갖는 chain이라면 다음과 같다.

$$
T_{standard}=O(N),
\qquad
M_{standard}=O(N)
$$

[Lecture 4의 backward pass](/posts/cs231n-lecture-4/#52-backward-pass)에서 local gradient가 forward input을 재사용한 이유가 그대로 memory 병목이 된다.

### **5.2 Full recomputation의 극단**

반대 극단은 마지막 activation만 남기고 backward가 activation을 요구할 때마다 input부터 다시 forward하는 방법이다.

![Activation을 버린 뒤 각 backward 단계마다 필요한 값을 처음부터 다시 계산하는 전체 과정]({{ '/assets/img/posts/cs231n-lecture-11/animations/full-activation-recomputation.gif' | relative_url }})

아무 중간 결과도 잠시 저장하지 않는 단순 schedule은 원래 forward와 backward의 $2N$회 계산에 매 단계의 재계산을 더한다.

$$
C_{total}
=
2N+\sum_{k=1}^{N-1}k
=
2N+\frac{N(N-1)}{2}
=O(N^2)
$$

의 compute와 $O(1)$ persistent activation memory를 갖는다. Memory는 작지만 깊은 network에서 재계산이 지나치게 많다.

### **5.3 Periodic checkpoint와 segment recomputation**

중간 지점에 checkpoint를 두면 두 극단 사이를 선택할 수 있다.

![일부 activation만 checkpoint로 남겨 재계산 범위를 제한하는 절충]({{ '/assets/img/posts/cs231n-lecture-11/animations/periodic-activation-checkpoints.gif' | relative_url }})

$K$개의 checkpoint만 persistent하게 남기고 각 activation을 필요할 때마다 가장 가까운 checkpoint에서 다시 만드는 단순 schedule은 다음과 같다.

$$
T=O\left(\frac{N^2}{K}\right),
\qquad
M=O(K)
$$

$K\approx\sqrt N$이면 $O(N\sqrt N)$ compute와 $O(\sqrt N)$ memory의 중간점이 된다.

실제 segment checkpointing은 더 효율적이다. $K$개의 segment boundary를 저장하고 backward 직전에 한 segment를 한 번 재실행하면서 내부 activation을 잠시 보관한다. 이때 peak activation memory와 compute는 대략 다음과 같다.

$$
M_{segment}
=
O\left(K+\frac{N}{K}\right)
$$

$$
T_{segment}=O(N)
$$

$K\approx\sqrt N$에서 memory는 $O(\sqrt N)$이고, compute는 원래 forward에 segment별 forward 한 번이 추가되는 constant-factor overhead다. PyTorch `torch.utils.checkpoint.checkpoint`도 checkpointed function을 backward에서 다시 실행하는 이 계열의 방법이다.

Activation checkpointing은 free memory를 larger local batch나 longer sequence로 바꾸지만 iteration은 느려진다. PP의 microbatch 수를 늘릴수록 살아 있는 activation도 늘기 때문에 checkpoint 강도와 pipeline schedule은 함께 조정해야 한다.

### **5.4 Memory 병목에 따른 확장 순서**

실무에서는 먼저 DDP로 compute를 복제하고, model state가 device memory를 넘으면 FSDP를 적용한다. 그 뒤 activation이 병목이면 checkpointing, 느린 inter-node link까지 sharding 통신이 퍼지면 HSDP를 고려한다. Sequence가 길거나 model이 깊고 넓어 한 축만으로 부족해질 때 CP·PP·TP를 더한다. 이 순서는 출발점이며, 최종 parallel degree는 실제 step time과 MFU를 측정해 결정한다.

## **6. HFU와 MFU 기반 throughput 측정**

### **6.1 Peak FLOPs와 kernel utilization**

Hardware FLOPs Utilization(HFU)은 cluster가 실제로 실행한 FLOPs가 theoretical peak의 어느 정도인지 나타낸다. $F_{peak}$는 GPU 한 장의 peak FLOP/s이고, $F_{executed}$는 한 global step 동안 전체 cluster가 실제로 수행한 FLOPs다.

$$
\mathrm{HFU}
=
\frac{F_{executed}}
{t_{step}N_{GPU}F_{peak}}
$$

![Matrix size에 따라 달라지는 H100의 hardware FLOPs utilization 측정]({{ '/assets/img/posts/cs231n-lecture-11/animations/hardware-flops-utilization.gif' | relative_url }})

큰 dense matrix multiplication은 Tensor Core를 오래 채우고 operand를 재사용하므로 높은 HFU를 얻기 쉽다. 작은 matrix는 launch overhead와 memory movement의 비중이 커져 utilization이 낮다.

GPU kernel launch는 비동기이므로 CPU wall-clock만 재면 enqueue 시간만 잡힐 수 있다. 정확한 step time은 warm-up 뒤 CUDA event를 사용하거나 측정 구간 전후에 `torch.cuda.synchronize()`를 호출해 얻는다.

HFU의 분자에는 activation recomputation처럼 hardware가 실제로 수행했지만 원래 model forward·backward에는 없던 FLOPs도 들어간다. 따라서 GPU가 바쁘다는 사실만으로 training algorithm이 효율적인 것은 아니다.

### **6.2 Useful model FLOPs와 iteration time**

Model FLOPs Utilization(MFU)은 원래 model의 useful forward·backward FLOPs만 분자에 둔다.

$$
\mathrm{MFU}
=
\frac{F_{model,step}}
{t_{step}N_{GPU}F_{peak}}
=
\frac{t_{theoretical}}{t_{actual}}
$$

![Model의 이론적 FLOPs와 실제 iteration time으로 MFU를 계산하고 Llama 3 수치로 연결하는 과정]({{ '/assets/img/posts/cs231n-lecture-11/animations/model-flops-utilization.gif' | relative_url }})

Dense decoder-only Transformer에서는 attention의 세부 항을 생략한 거친 근사로 parameter 수 $P$와 global step 전체 token 수 $T$에 대해

$$
F_{model,step}\approx6PT
$$

를 자주 사용한다. Forward가 약 $2PT$, backward가 그 두 배라는 matrix-multiplication 근사다.

MFU를 낮추는 항목은 다음과 같다.

- Collective communication과 synchronization 대기
- Pipeline bubble과 stage imbalance
- Activation recomputation
- Data loading과 preprocessing stall
- Tensor Core를 충분히 채우지 못하는 작은 kernel
- Python·CPU launch overhead

30% 이상을 양호하고 40% 이상을 매우 높은 값으로 보는 기준은 대규모 dense training에서의 경험칙이다. MFU는 model quality가 아니라 throughput metric이며, batch size와 optimization 제약을 만족하는 configuration 사이에서 비교해야 한다.

새 GPU는 compute peak가 interconnect와 memory bandwidth보다 빠르게 증가할 수 있다. 이 경우 device 자체는 더 빠르지만 communication 비중이 커져 cluster MFU가 오히려 낮아질 수 있다. 그래서 parallel degree를 고르는 기준은 FLOPs 표가 아니라 end-to-end step time과 MFU다.

## **7. Context Parallelism과 long sequence**

Context Parallelism(CP)은 하나의 sequence를 token 축으로 나눈다. Sequence length $S$를 $d_{CP}$개 rank로 나누면 각 rank는 대략 $S/d_{CP}$ token의 activation을 가진다.

![Transformer block의 token-local 연산과 global attention에서 Ring Attention·Ulysses로 이어지는 Context Parallelism]({{ '/assets/img/posts/cs231n-lecture-11/animations/context-parallelism.gif' | relative_url }})

### **7.1 Token-local block과 global attention**

LayerNorm·RMSNorm은 learnable scale을 가질 수 있지만 각 token의 hidden dimension 안에서 독립적으로 계산된다. MLP와 residual도 token-local이므로 sequence shard마다 바로 실행할 수 있다. 다만 MLP와 QKV projection weight를 rank마다 복제하면 backward에서 rank별 partial weight gradient를 합쳐야 한다.

어려운 부분은 self-attention이다. 각 local query는 sequence 전체의 key와 value를 봐야 한다.

$$
O_i
=
\operatorname{softmax}
\left(
\frac{Q_iK^\top}{\sqrt{d_h}}
\right)V
$$

$Q_i$는 rank $i$의 local query지만 $K,V$는 global sequence를 포함해야 한다. [Lecture 8의 QKV 계산](/posts/cs231n-lecture-8/#3-querykeyvalue를-이용한-attention의-일반화)과 [dense attention의 quadratic cost](/posts/cs231n-lecture-8/#52-dense-attention의-quadratic-cost와-flashattention)가 이제 device 사이의 communication 문제로 바뀐다.

### **7.2 Ring Attention의 KV block 순환**

Ring Attention은 각 rank가 local query block을 고정하고 key·value block을 ring을 따라 순환시킨다. 한 block의 attention을 계산하는 동안 다음 KV block을 전송해 communication과 compute를 겹친다.

전체 score matrix를 한 GPU에 만들지 않고 numerically stable online softmax로 partial result를 합치면 exact attention output을 얻을 수 있다. Sequence가 길어져도 rank 수에 비례해 KV storage와 block compute를 분산할 수 있다.

### **7.3 Ulysses의 sequence-to-head all-to-all**

Ulysses는 attention 직전에 layout을 바꾼다.

1. 시작: 각 rank가 전체 head의 일부 sequence token 보유
2. `all-to-all`: 각 rank가 전체 sequence의 일부 attention head 보유
3. Head별 attention의 독립 계산
4. 역방향 `all-to-all`: sequence-sharded layout 복원

구조가 단순하고 head 단위 병렬성이 좋지만 parallel degree가 attention head 수의 제약을 받는다. GQA처럼 KV head 수가 적은 architecture에서는 layout 설계가 더 중요하다.

Llama 3의 한 사례에서는 sequence length 8192 단계에 CP를 쓰지 않고, 131072 단계에서 16-way CP를 사용했다. 결과적으로 한 CP rank가 담당하는 token 수는 다시 8192가 된다.

$$
\frac{131072}{16}=8192
$$

## **8. Pipeline Parallelism과 bubble**

Pipeline Parallelism(PP)은 연속된 layer 구간을 서로 다른 GPU stage에 배치한다. Forward activation은 다음 stage로, backward gradient는 이전 stage로 이동한다.

![Layer partition에서 idle bubble과 여러 microbatch를 이용한 pipeline schedule로 이어지는 과정]({{ '/assets/img/posts/cs231n-lecture-11/animations/pipeline-parallel-microbatches.gif' | relative_url }})

### **8.1 Microbatch 기반 pipeline 충전**

한 batch만 pipeline에 넣으면 뒤 stage가 forward input을 기다리고 앞 stage가 backward gradient를 기다린다. 이 빈 구간이 bubble이다.

$P$개 stage에 $m$개 microbatch를 사용하는 이상적인 fill-drain schedule의 stage utilization은 다음과 같다.

$$
U_{pipe}
=
\frac{m}{m+P-1}
$$

$P=4,m=4$이면

$$
U_{pipe}
=
\frac{4}{7}
\approx57.1\%
$$

이다. 이는 communication, kernel efficiency와 stage imbalance를 제외한 이상적 pipeline 가동률이지 end-to-end MFU 자체는 아니다.

Microbatch 수를 늘리면 bubble 비율은 작아지지만 여러 microbatch의 activation이 동시에 살아 있어 memory가 늘어난다. Microbatch가 너무 작으면 matrix multiplication도 작아져 HFU가 낮아질 수 있다. 따라서 PP degree, microbatch 수, activation checkpointing과 local batch를 함께 조정해야 한다.

---

## **9. Tensor Parallelism과 block matrix multiplication**

Tensor Parallelism(TP)은 한 layer의 weight matrix 자체를 여러 GPU에 나눈다. Input을

$$
X\in\mathbb{R}^{N\times D}
$$

라고 하자.

![한 linear layer의 output-dimension 분할에서 두 linear layer의 column·row pairing으로 이어지는 Tensor Parallelism]({{ '/assets/img/posts/cs231n-lecture-11/animations/tensor-parallel-block-matmul.gif' | relative_url }})

### **9.1 Column-parallel·row-parallel linear pair**

첫 번째 weight를 output dimension으로 $p$개 분할한다.

$$
W=[W_1\;W_2\;\cdots\;W_p],
\qquad
W_i\in\mathbb{R}^{D\times D/p}
$$

각 rank는 다음 local output을 계산한다.

$$
Y_i=XW_i,
\qquad
Y_i\in\mathbb{R}^{N\times D/p}
$$

일반적으로 다음 layer가 full $Y$를 요구하면 $Y_i$의 all-gather가 필요하다. 그러나 Transformer FFN처럼 두 linear layer 사이에 element-wise activation $\phi$가 있으면 두 번째 weight를 input dimension으로 나눌 수 있다.

$$
U=
\begin{bmatrix}
U_1\\U_2\\\vdots\\U_p
\end{bmatrix},
\qquad
U_i\in\mathbb{R}^{D/p\times D}
$$

각 rank는 local partial output을 만든다.

$$
Z_i=\phi(Y_i)U_i,
\qquad
Z_i\in\mathbb{R}^{N\times D}
$$

마지막에 합산 all-reduce를 수행한다.

$$
Z
=
\sum_{i=1}^{p}Z_i
\in
\mathbb{R}^{N\times D}
$$

첫 layer와 두 번째 layer 사이에는 $Y$ all-gather가 필요하지 않다. Frequent collective가 발생하는 TP는 보통 가장 빠른 intra-node link에 배치한다.

## **10. ND Parallelism과 physical topology**

가장 큰 model은 네 방식 중 하나를 고르는 대신 네 축을 동시에 사용한다.

![Data·Context·Pipeline·Tensor Parallelism의 동시 사용과 Llama 3 configuration]({{ '/assets/img/posts/cs231n-lecture-11/animations/nd-parallelism.gif' | relative_url }})

Llama 3 405B의 예시는 같은 16M token global batch를 유지하면서 sequence length에 따라 parallel degree를 바꾸는 모습을 보여 준다.

| GPUs | TP | CP | PP | DP | Sequence | MFU |
|---:|---:|---:|---:|---:|---:|---:|
| 8192 | 8 | 1 | 16 | 64 | 8192 | 43% |
| 16384 | 8 | 1 | 16 | 128 | 8192 | 41% |
| 16384 | 8 | 16 | 16 | 8 | 131072 | 38% |

같은 16384 GPUs를 사용한 마지막 두 row를 비교하면 sequence가 16배 길어지면서 CP가 1에서 16으로 증가하고 DP가 128에서 8로 줄어든다. **동일한 4D rank grid를 workload의 다른 축에 재배치한 것**이다.

일반적인 배치 원칙은 다음과 같다.

- TP: 매 layer의 frequent collective 때문에 가장 빠른 local link
- FSDP/CP: parameter·KV communication을 감당할 고속 group
- PP: stage boundary의 point-to-point communication과 균형 잡힌 layer partition
- DP replica: 상대적으로 넓은 cluster domain

정답 configuration은 model shape, batch, sequence, network topology와 kernel efficiency에 따라 바뀐다. 최종 선택 기준은 각 축의 이론적 크기가 아니라 실제 MFU다.

## **11. PyTorch 기반 분산 연산 검산**

### **11.1 Data-parallel gradient의 등가성**

두 local batch의 평균 gradient가 global batch gradient와 같은지 CPU에서도 확인할 수 있다.

```python
import torch
import torch.nn.functional as F
from torch import nn

torch.manual_seed(0)

model = nn.Linear(4, 3, bias=False)
x = torch.randn(12, 4)
target = torch.randn(12, 3)


def weight_gradient(x_part, target_part):
    prediction = model(x_part)
    loss = F.mse_loss(prediction, target_part, reduction="mean")
    return torch.autograd.grad(loss, model.weight)[0]


global_gradient = weight_gradient(x, target)
local_gradients = [
    weight_gradient(x_part, target_part)
    for x_part, target_part in zip(x.chunk(2), target.chunk(2))
]
reduced_gradient = torch.stack(local_gradients).mean(dim=0)

torch.testing.assert_close(global_gradient, reduced_gradient)
print(global_gradient.shape)
# torch.Size([3, 4])
```

실제 DDP는 이 평균을 gradient bucket의 all-reduce로 수행하고 backward와 overlap한다.

### **11.2 Tensor-parallel linear pair의 등가성**

첫 weight의 output dimension과 둘째 weight의 input dimension을 같은 방식으로 나누면 중간 all-gather 없이 full MLP 결과를 복원할 수 있다.

```python
import torch
import torch.nn.functional as F

torch.manual_seed(0)

tokens, hidden, parallel_size = 5, 8, 4
x = torch.randn(tokens, hidden)
w = torch.randn(hidden, hidden)
u = torch.randn(hidden, hidden)

w_shards = w.chunk(parallel_size, dim=1)
u_shards = u.chunk(parallel_size, dim=0)

y_shards = [x @ w_i for w_i in w_shards]
z_shards = [F.gelu(y_i) @ u_i for y_i, u_i in zip(y_shards, u_shards)]
tensor_parallel_output = torch.stack(z_shards).sum(dim=0)

reference_output = F.gelu(x @ w) @ u
torch.testing.assert_close(tensor_parallel_output, reference_output)

print(y_shards[0].shape, tensor_parallel_output.shape)
# torch.Size([5, 2]) torch.Size([5, 8])
```

`torch.stack(...).sum(dim=0)`이 실제 distributed implementation의 all-reduce에 해당한다.

## **12. 정리**

Large-scale distributed training은 다음 연결로 정리된다.

1. Tensor Core를 채우는 큰 matrix computation과 memory hierarchy
2. Device·server·pod마다 달라지는 communication bandwidth
3. Batch를 나누고 gradient를 동기화하는 Data Parallelism
4. Model state를 shard하고 필요할 때만 모으는 FSDP
5. Network hierarchy를 반영하는 HSDP group
6. Activation을 재계산해 memory를 절약하는 checkpointing
7. Useful model throughput을 측정하는 MFU
8. Sequence·layer·hidden dimension을 나누는 CP·PP·TP
9. 네 축을 하나의 rank grid에 배치하는 ND parallelism

좋은 distributed configuration은 GPU를 가장 많이 쓰는 configuration이 아니다. **Model shape와 physical network에 맞는 축으로 일을 나누고, 추가 통신과 재계산을 포함한 실제 iteration에서 가장 높은 MFU를 만드는 configuration**이다.
